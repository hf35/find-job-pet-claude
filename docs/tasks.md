# План работ

Проект делается небольшими этапами. Каждый этап — отдельный PR, после которого сервис остаётся рабочим.
Отмечайте `[x]` выполненные пункты в том же PR, где они сделаны.

Легенда: `[ ]` — не начато, `[~]` — в работе, `[x]` — готово.

---

## Этап 0. Каркас проекта

Цель: пустое, но собирающееся приложение — сервер отдаёт API и собранный фронтенд.

- [x] npm workspaces: `server/` (Fastify + TypeScript) и `web/` (React + Vite + TypeScript)
- [x] Общие настройки: TypeScript strict, ESM, ESLint, Prettier, Vitest
- [x] Конфигурация через env с валидацией (zod), файл `.env.example`
- [x] `GET /api/health` → `{ status: "ok", version }`
- [x] Fastify раздаёт собранный `web/dist` как статику, SPA-fallback на `index.html`
- [x] Скрипты: `dev` (сервер + Vite с прокси), `build`, `start`, `lint`, `test`, `typecheck`

**Готово, когда:** `npm run build && npm start` поднимает приложение на `:8844`, страница открывается, health отвечает.

## Этап 1. Docker и CI/CD

Цель: образ собирается на GitHub и запускается на VPS за Caddy.

- [x] Multi-stage `Dockerfile` (сборка → slim runtime, non-root пользователь), `HEALTHCHECK`
- [x] Данные (SQLite) в volume `/data`
- [x] `docker-compose.yml` для VPS: `127.0.0.1:8844:8844`, volume, `env_file`
- [x] GitHub Actions:
  - [x] на PR: lint, typecheck, test, сборка образа (без публикации)
  - [x] на push в `main` и теги `v*`: публикация в GHCR (`ghcr.io/hf35/find-job-pet-claude`, теги `latest`, `sha-…`, версия)
- [x] `docs/deploy.md`: запуск на VPS, пример блока Caddy, обновление образа

**Готово, когда:** после merge в `main` образ появляется в GHCR и стартует через `docker compose up -d`.

## Этап 2. База данных

Цель: схема хранения и миграции.

- [x] SQLite (`better-sqlite3`) + Drizzle ORM, миграции применяются при старте
- [x] Таблицы (первая версия):
  - `searches` — поисковые профили (параметры источника + правила фильтрации, JSON)
  - `vacancies` — нормализованные вакансии + сырой ответ источника (`raw` JSON), уникальность `(source, external_id)`
  - `search_vacancies` — какими поисками найдена вакансия
  - `vacancy_state` — статус пользователя: new / liked / disliked / hidden / applied
  - `filter_results` — прошла ли правила и почему отсеяна
  - `analyses` — результат LLM (оценка, плюсы, минусы, флаги, модель, хеш профиля)
  - `letters` — сопроводительные письма (версии)
  - `profile` — резюме и предпочтения (одна запись)
  - `runs` — журнал запусков (время, счётчики, ошибки)
- [x] Файл БД по пути из env (`DATABASE_PATH`, по умолчанию `/data/app.sqlite`), WAL-режим

## Этап 3. Авторизация

Цель: доступ к интерфейсу только по паролю.

- [ ] Пароль задаётся bcrypt-хешем в env `ADMIN_PASSWORD_HASH`, логин — `ADMIN_USERNAME`
- [ ] Скрипт `npm run hash-password` для генерации хеша
- [ ] Сессия в подписанной httpOnly cookie (`SESSION_SECRET`), `Secure`, `SameSite=Lax`
- [ ] Rate limit на `/api/auth/login`
- [ ] Все `/api/*`, кроме health и login, требуют сессию
- [ ] Страница входа и кнопка «Выйти» во фронтенде

## Этап 4. Адаптер hh.ru

Цель: получать вакансии по параметрам поиска.

- [ ] Сверить актуальные требования `dev.hh.ru` (User-Agent, токен приложения, лимиты) и описать в `docs/hh-api.md`
- [ ] Общий интерфейс источника: `search(params) → VacancyRef[]`, `getDetails(id) → Vacancy`
- [ ] HTTP-клиент: обязательный `HH-User-Agent`/`User-Agent` из env, ретраи с backoff, ограничение частоты запросов
- [ ] Пагинация (`per_page=100`, учитывать лимит глубины выдачи hh)
- [ ] Загрузка полного описания вакансии (`/vacancies/{id}`) только для новых или изменившихся
- [ ] Нормализация в общую модель `Vacancy` (название, компания, зарплата, регион, формат, опыт, навыки, описание, ссылка, даты)
- [ ] Кеш справочников hh (`/dictionaries`, `/areas`, `/professional_roles`) с обновлением раз в сутки
- [ ] Unit-тесты нормализации на сохранённых фикстурах ответов

## Этап 5. Поиски — слой 1 (параметры источника)

Цель: создать и настроить поисковые профили из интерфейса.

- [ ] CRUD поисков в API и UI, переключатель вкл/выкл
- [ ] Форма параметров hh: поисковая строка (+ «только в названии»), регионы (мультиселект с поиском по дереву), формат работы, опыт, занятость, зарплата/валюта/«только с зарплатой», проф. роль
- [ ] Кнопка «Проверить»: число найденных вакансий и первые 5–10 названий без сохранения

## Этап 6. Пайплайн и планировщик

Цель: регулярный сбор вакансий.

- [ ] Пайплайн: для каждого активного поиска → выдача → дедупликация → загрузка деталей новых → сохранение → фильтры → (позже) LLM
- [ ] Планировщик `node-cron`, расписание из env (`CRON_SCHEDULE`, по умолчанию раз в 6 часов)
- [ ] Блокировка от параллельных запусков
- [ ] Кнопка «Запустить сейчас» и страница журнала запусков (найдено / новых / отфильтровано / проанализировано / ошибки)
- [ ] Отметка вакансий, пропавших из выдачи или закрытых на hh (архив)

## Этап 7. Правила фильтрации — слой 2

Цель: бесплатно отсеять лишнее до LLM.

- [ ] Теги стека с тремя состояниями: обязательно / плюс / исключить (поиск по названию, описанию, ключевым навыкам; без учёта регистра, с синонимами вида `Node.js = NodeJS = Node`)
- [ ] Стоп-слова в названии
- [ ] Чёрный список компаний (глобальный + на уровне поиска)
- [ ] Политика вакансий без зарплаты: пропускать / показывать
- [ ] Чистая функция `applyRules(vacancy, rules) → { passed, reasons, bonus }` с unit-тестами
- [ ] UI: редактор тегов с переключением состояния, причина отсева видна в ленте («показать отсеянные»)

## Этап 8. Лента вакансий

Цель: удобно просматривать результаты.

- [ ] Список с сортировкой (оценка, дата, зарплата) и фильтрами (статус, поиск, источник, «только новые»)
- [ ] Карточка: ключевые поля, описание, навыки, какими поисками найдена, ссылка на hh
- [ ] Действия: 👍 / 👎 / скрыть / «откликнулся», «компанию в чёрный список»
- [ ] Счётчик новых с последнего просмотра

## Этап 9. Профиль — слой 3

- [ ] Страница профиля: резюме (текст), предпочтения и красные флаги свободным текстом
- [ ] Примеры своих удачных сопроводительных писем (для стиля)

## Этап 10. LLM-клиент

Цель: единый доступ к любой модели через OpenAI-совместимый API.

- [ ] Конфигурация: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`; отдельная модель для писем (`LLM_LETTER_MODEL`, опционально)
- [ ] Цепочка резервных провайдеров при ошибках и лимитах (429)
- [ ] Структурированный ответ: JSON + валидация zod, повтор при невалидном ответе
- [ ] Ограничение параллельности и частоты запросов, логирование расхода токенов
- [ ] Проверка подключения из UI («Тест LLM»)

## Этап 11. Анализ вакансий

- [ ] Промпт: профиль + вакансия → `{ score 0–100, summary, pros[], cons[], redFlags[], stackMatch, salaryEstimate? }`
- [ ] Анализ только для вакансий, прошедших правила; лимит на один запуск
- [ ] Кеш по `vacancy_id + хеш профиля + модель`; кнопка «переанализировать»
- [ ] Итоговый рейтинг = оценка LLM + бонус из правил; сортировка ленты по нему
- [ ] Отображение анализа в карточке

- [ ] Генерация по резюме, вакансии, анализу и примерам писем
- [ ] Редактирование, сохранение версий, кнопка «Скопировать»
